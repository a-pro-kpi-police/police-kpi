# Техническая спецификация проекта KPI полиции

Дата актуализации: 2026-09-01.

## 1. Назначение системы

Система KPI полиции предназначена для электронного учета результатов работы сотрудников полиции, проверки записей начальником подразделения, расчета итоговых KPI-баллов и анализа эффективности по сотрудникам, участкам и периодам.

Система заменяет ручное ведение KPI-таблиц и обеспечивает:

- единый справочник KPI-показателей;
- ввод фактических результатов работы сотрудниками и руководителями;
- прикрепление подтверждающих материалов;
- workflow подтверждения или отклонения записей;
- расчет баллов с учетом лимитов, коэффициентов участков, массовых и критических показателей;
- назначение индивидуальных и групповых целей;
- дашборды, рейтинги, уведомления и внутренний мессенджер.

## 2. Состав проекта

Проект является веб-приложением с клиент-серверной архитектурой.

| Компонент | Путь | Назначение |
|---|---|---|
| Frontend | `frontend/` | React-приложение для пользователей системы |
| Backend Go | `backend-golang/` | Основной HTTP API, бизнес-логика, работа с PostgreSQL |
| Legacy backend | `backend/` | Старый Python/FastAPI backend, не является основным production-компонентом |
| Deploy | `docker-compose.yml`, `docker-compose.prod.yml`, `deploy/` | Docker Compose и примеры nginx-конфигурации |
| Docs | `docs/` | Документация по деплою и техническая спецификация |
| Scripts | `scripts/` | Вспомогательные скрипты экспорта/подготовки данных |

Основной стек:

- Backend: Go 1.24, `net/http`, PostgreSQL, `github.com/lib/pq`, опционально SQLite для легких локальных проверок.
- Frontend: React 18, Vite 5, React Router 6, Axios, Recharts.
- Хранилище: PostgreSQL 16.
- Доставка: Docker Compose; production frontend собирается в статический билд и отдается через nginx.

## 3. Роли пользователей

В системе используются три роли.

| Роль | Код роли | Назначение |
|---|---|---|
| Администратор | `admin` | Управляет пользователями, начальниками, сотрудниками и активным справочником KPI |
| Начальник отдела | `head` | Проверяет KPI-записи, назначает цели, смотрит дашборды и рейтинги по доступному участку |
| Сотрудник | `officer` | Создает свои KPI-записи, смотрит собственные цели, записи, уведомления и диалог с начальником |

Правила доступа:

- Все рабочие API, кроме входа, требуют Bearer JWT.
- Администратор имеет отдельный интерфейс `/admin`, `/admin/catalog`, `/admin/rating`.
- Начальник видит дашборд, записи, цели, рейтинг и мессенджер.
- Сотрудник по умолчанию попадает в `/entries` и видит только собственные записи и цели.
- Если начальник привязан к участку, его доступ ограничивается сотрудниками этого участка.
- Администратор не участвует в мессенджере.

## 4. Основные пользовательские сценарии

### 4.1 Вход в систему

1. Пользователь вводит логин и пароль на странице `/login`.
2. Frontend отправляет `POST /api/auth/login` в формате `application/x-www-form-urlencoded`.
3. Backend проверяет пароль, выдает JWT с TTL 12 часов.
4. Frontend сохраняет токен в `localStorage` и запрашивает `GET /api/auth/me`.
5. При ответе API `401` frontend удаляет токен и возвращает пользователя на страницу входа.

### 4.2 Создание KPI-записи сотрудником

1. Сотрудник открывает экран “Мои записи”.
2. Выбирает KPI из активного справочника, вводит количество, дату, комментарий.
3. При необходимости прикрепляет файл до 20 МБ.
4. Backend создает запись со статусом `pending`.
5. Начальники, подходящие по участку, получают уведомление о новой записи.
6. Запись попадает в очередь рассмотрения начальника.

### 4.3 Проверка KPI-записи начальником

1. Начальник открывает экран записей KPI.
2. Фильтрует записи по сотруднику, периоду, статусу.
3. Просматривает подтверждающие сведения и вложение.
4. Подтверждает (`confirmed`) или отклоняет (`rejected`) запись, при необходимости оставляет резолюцию.
5. Backend пересчитывает KPI сотрудника за месяц.
6. Сотрудник получает уведомление о смене статуса.

### 4.4 Назначение целей

1. Начальник открывает экран целевых KPI.
2. Выбирает сотрудника или группу по участку.
3. Выбирает месяц и KPI-показатели из положительного активного справочника.
4. Задает целевые количества.
5. Backend сохраняет цели в `kpi_targets`.
6. Сотрудник видит прогресс по целям на своем экране записей.

### 4.5 Аналитика и рейтинг

1. Начальник открывает дашборд.
2. Выбирает месяц, участок или сотрудника.
3. Система показывает итоговые баллы, статусы записей, выполнение цели, тренды, распределение по блокам, влияние лимитов и критических показателей.
4. Рейтинг сортирует сотрудников по подтвержденным итоговым баллам.

### 4.6 Внутренний мессенджер

1. Начальник и сотрудник открывают доступный диалог.
2. Сообщение может быть отправлено как обычный текст или с привязкой к KPI-записи.
3. Получатель видит счетчик непрочитанных сообщений.
4. Отправитель может удалить свое сообщение; у участников оно отображается как удаленное.

## 5. Функциональные требования

### 5.1 Авторизация и профиль

- Система должна поддерживать вход по логину и паролю.
- Пароли должны храниться только в виде PBKDF2-HMAC-SHA256 хэша с солью.
- JWT должен подписываться алгоритмом HS256.
- Токен должен содержать идентификатор пользователя, роль и срок действия.
- Система должна возвращать текущий профиль пользователя через `GET /api/auth/me`.

### 5.2 Управление пользователями

- Администратор должен иметь возможность получать список начальников и сотрудников.
- Администратор должен создавать, редактировать и удалять начальников и сотрудников.
- Для пользователя должны храниться логин, ФИО, звание, роль, участок, табельный номер и месячная норма.
- Логин должен быть уникальным.
- Табельный номер, если задан, должен быть уникальным.
- Для сотрудника участок обязателен.
- Месячная норма должна быть больше нуля.
- Удаление пользователя должно удалять связанные KPI-записи, цели, уведомления, сообщения и файлы вложений.
- Системный пользователь `admin` не должен удаляться или изменяться через обычные CRUD-операции сотрудников.

### 5.3 Справочник KPI

- Система должна хранить активный справочник KPI.
- KPI должен содержать код, название показателя, блок, подблок, НПА/статью, баллы за единицу, единицу измерения, ссылку на источник, месячный лимит, признаки массового и критического показателя.
- Код KPI должен быть уникальным.
- Публичный рабочий справочник должен отдавать только активные KPI.
- Для сотрудников справочник не должен включать отрицательные KPI.
- Для начальников и администраторов рабочий справочник может включать отрицательные KPI.
- Администраторский справочник целевых KPI должен работать только с активными неотрицательными показателями.
- Удаление KPI администратором должно деактивировать запись (`is_active = 0`) и удалить связанные цели, не удаляя исторические KPI-записи.

### 5.4 KPI-записи

- Сотрудник должен создавать записи только за себя.
- Начальник и администратор должны создавать записи за выбранного сотрудника в рамках своих прав.
- Новая запись должна получать статус `pending`.
- Количество должно быть больше нуля.
- Дата должна иметь формат `YYYY-MM-DD`; месяц записи определяется как `YYYY-MM`.
- Сотрудник не может создавать KPI с отрицательным баллом.
- Начальник и администратор могут создавать отрицательные KPI, если показатель доступен в справочнике.
- Запись должна поддерживать комментарий сотрудника и резолюцию начальника.
- Начальник и администратор должны менять статус записи на `pending`, `confirmed` или `rejected`.
- При подтверждении, отклонении или удалении записи система должна пересчитывать KPI сотрудника за соответствующий месяц.
- Начальник с привязкой к участку не должен видеть или изменять записи сотрудников других участков.
- Список записей должен поддерживать фильтры по сотруднику, месяцу, кварталу, году, статусу, сортировку и пагинацию.
- Пагинационный `limit` должен быть от 1 до 100.

### 5.5 Вложения

- Запись должна поддерживать несколько вложений: до 5 файлов за один запрос.
- Максимальный размер одного файла: 20 МБ.
- Разрешенные расширения: `.csv`, `.doc`, `.docx`, `.jpeg`, `.jpg`, `.pdf`, `.png`, `.txt`, `.webp`, `.xls`, `.xlsx`, `.zip`, `.mp4`, `.webm`, `.ogv`.
- Файл должен храниться на диске/volume, а в БД должны храниться оригинальное имя, внутреннее имя, MIME-тип и размер.
- Скачать вложение может начальник/администратор с правом доступа к записи или сам сотрудник-владелец.
- API скачивания должен отдавать исходный MIME-тип с `Content-Disposition: attachment`.
- Видео должно воспроизводиться встроенным HTML5-плеером через временный URL, ограниченный конкретными записью и вложением.
- API воспроизведения должен поддерживать HTTP byte-range запросы и возвращать `206 Partial Content`, чтобы работала перемотка.

### 5.6 Расчет KPI

Расчет выполняется для подтвержденных записей сотрудника за месяц.

Для каждой записи:

- `raw_score = quantity * points_per_unit`;
- если у KPI задан `monthly_limit > 0`, в расчет попадает не больше лимита;
- `counted_quantity` показывает количество, зачтенное после лимита;
- `capped_score = counted_quantity * points_per_unit`;
- коэффициент участка берется из участка сотрудника, при отсутствии участка используется `1.0`;
- промежуточные значения округляются до двух знаков.

Для месяца:

- положительные и отрицательные KPI учитываются раздельно;
- массовая доля считается как `mass_score / positive_score`;
- если массовая доля больше 40%, применяется коэффициент `0.85`;
- если массовая доля больше 60%, применяется коэффициент `0.70`;
- если массовая доля не превышает 40%, применяется коэффициент `1.0`;
- положительные баллы умножаются на массовый коэффициент и коэффициент участка;
- отрицательные баллы уменьшают итоговый результат;
- итог не может быть меньше нуля;
- если подтвержден хотя бы один критический KPI с количеством больше нуля, итоговый результат сотрудника за месяц равен нулю;
- месячная эффективность сравнивается с месячной нормой пользователя, по умолчанию 100 баллов.

При превышении месячного лимита одного KPI несколькими записями лимит распределяется по подтвержденным записям в порядке даты и идентификатора записи.

### 5.7 Цели KPI

- Цели задаются на месяц в формате `YYYY-MM`.
- Цель не может быть отрицательной.
- Цели могут назначаться индивидуально сотруднику или массово группе сотрудников участка.
- В целях должны использоваться только активные положительные KPI.
- Прогресс по цели должен показывать целевое количество, подтвержденное количество, зачтенное количество, остаток, целевые баллы, фактические баллы и процент выполнения.
- Общий `target_score` сотрудника должен равняться его месячной норме; если норма равна нулю, используется 100.
- Сводка начальника должна показывать сотрудников ниже цели, без цели и в цели.

### 5.8 Дашборд

Дашборд доступен начальнику отдела.

Система должна показывать:

- сумму подтвержденных итоговых баллов;
- количество подтвержденных, ожидающих и отклоненных записей;
- количество сотрудников;
- долю подтверждения по рассмотренным положительным KPI;
- рейтинг сотрудников по итоговым баллам;
- распределение баллов по KPI-блокам;
- динамику итоговых баллов по месяцам;
- динамику статусов записей;
- объем работы по KPI-показателям;
- очередь и отклонения по участкам;
- сравнение выбранного сотрудника с прошлым периодом и коллегами;
- сотрудников без активности;
- влияние месячных лимитов;
- KPI с наибольшими превышениями лимитов;
- влияние критических показателей.

Дашборд должен поддерживать фильтры по месяцу, сотруднику и участку с учетом прав доступа начальника.

### 5.9 Рейтинг и эффективность

- Рейтинг должен включать сотрудников, их участок, звание, итоговые баллы, количество подтвержденных и ожидающих записей.
- Сортировка рейтинга по умолчанию должна идти от большего количества итоговых баллов к меньшему.
- При равенстве баллов сотрудники сортируются по ФИО.
- Эффективность сотрудника должна включать место в рейтинге, общее количество сотрудников и балл.
- Процент рейтинга рассчитывается как `баллы сотрудника / средний балл × 50`. Среднее включает всех сотрудников системы за тот же период, включая сотрудников с нулевыми баллами. Фильтры роты, сотрудника, имени и категории и область доступа к списку не меняют среднее. Сервер передаёт только общий агрегат `global_average_score`, персональные данные остаются ограничены правами доступа. В API рейтинга агрегат добавлен к каждой доступной строке без изменения формата массива; в API дашборда — в корень ответа.
- Общее среднее KPI равно сумме баллов всех сотрудников системы, делённой на количество этих сотрудников. Каждый сотрудник имеет одинаковый вес независимо от численности роты; средние значения рот не усредняются. Например, 10 сотрудников с KPI 100 и 30 сотрудников с KPI 60 дают `(10 × 100 + 30 × 60) / 40 = 70`.
- Категории определяются по неокругленному проценту:
  - «Высокоэффективные»: больше 66%;
  - «Эффективные»: больше 33% и не больше 66%;
  - «Неэффективные»: не больше 33%.
- При нулевом среднем показываются 0% и категория «Неэффективные»; пустая выборка не вызывает деления на ноль.
- Отображаемое «Выполнение» ограничено 100% и округляется до одного десятичного знака. Исходные баллы не ограничиваются.
- Рейтинг начальника, рейтинг администратора и месячная сводка категорий на дашборде используют общую логику расчета.

### 5.10 Уведомления

- Пользователь должен видеть список уведомлений и количество непрочитанных.
- По умолчанию API должен возвращать 20 уведомлений.
- Максимальный лимит выдачи уведомлений: 100.
- Пользователь может отметить одно уведомление или все свои уведомления как прочитанные.
- Система должна создавать уведомление начальнику при новой записи сотрудника.
- Система должна создавать уведомление сотруднику при смене статуса записи на `confirmed` или `rejected`.

### 5.11 Мессенджер

- Мессенджер доступен начальнику и сотруднику.
- Диалог разрешен только между начальником и сотрудником.
- Если у начальника и сотрудника указаны участки, диалог разрешен только в пределах одного участка.
- Сообщение не может быть пустым.
- Максимальная длина сообщения: 2000 символов.
- Сообщение может ссылаться на KPI-запись, доступную в рамках данного диалога.
- При открытии диалога непрочитанные сообщения должны отмечаться прочитанными.
- Отправитель может удалить свое сообщение; физически запись сообщения сохраняется, но получает `deleted_at`.

### 5.12 Локализация и интерфейс

- Frontend должен поддерживать русский и казахский языки.
- Выбранный язык должен сохраняться в `localStorage`.
- Интерфейс должен поддерживать светлую и темную темы.
- Выбранная тема должна сохраняться в `localStorage`.
- Навигация должна зависеть от роли пользователя.
- Все API-запросы frontend должны идти через базовый путь `/api`.

### 5.13 Импорт данных

- Backend должен синхронизировать справочник из `backend-golang/kpi_catalog.csv` при запуске.
- Система должна создавать системного администратора при первом запуске.
- Режимы начального заполнения:
  - `catalog_only`: только справочник KPI и системный администратор;
  - `monthly_import`: импорт месячного CSV-снимка;
  - `demo`: демо-участки, начальник, сотрудники и тестовые KPI-записи.
- Месячный импорт должен быть идемпотентным по SHA-256 checksum файла.
- Импортируемый месячный файл должен содержать один месяц.
- При месячном импорте создается запись в `import_batches`.
- Импортированные KPI-записи должны иметь `is_monthly_aggregate = 1`, уникальный `source_key` и статус `confirmed`.
- Скрипт `scripts/export_monthly_numbers.js` должен восстанавливать CSV-снимок и справочник из исходного Numbers-файла на macOS.

### 5.14 Массовый импорт сотрудников

- CLI `go run ./cmd/import-users` должен импортировать сотрудников из CSV.
- CSV должен содержать `employee_number`, `full_name`, `rank`, `district`, `monthly_norm`.
- Существующие сотрудники должны сопоставляться по табельному номеру.
- Логин должен генерироваться латиницей по правилу `имя.первая_буква_фамилии`.
- При конфликте логина должен добавляться числовой суффикс.
- Пароли должны генерироваться и сохраняться только в output CSV; в БД хранится хэш.
- Флаг `-dry-run` должен позволять проверить импорт без сохранения изменений.
- Флаг `-reset-existing-passwords` должен позволять пересоздать пароли существующим сотрудникам.

## 8. Архитектура backend

Backend Go построен вокруг стандартного `net/http` и разделен на слои:

- `main.go`: запуск HTTP-сервера.
- `app.go`: конфигурация БД, middleware, маршруты, helper-функции ответа.
- `db.go`: диалекты PostgreSQL/SQLite, schema bootstrap, SQL placeholder rebind.
- `handlers_*.go`: HTTP-обработчики модулей.
- `internal/domain/*`: доменные политики и чистые правила.
- `internal/application/*`: application services, координация политик и репозиториев.
- `internal/infrastructure/*`: SQL-репозитории.
- `seed.go`, `internal/infrastructure/bootstrap/seed.go`: начальное заполнение, CSV-импорт, демо-данные.

Middleware:

- CORS: разрешены `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `OPTIONS`.
- Logging: логируются метод, путь, статус, размер ответа и длительность.
- Recovery: приложение должно восстанавливаться после panic и возвращать `500`.

Backend должен слушать порт из `PORT`, по умолчанию `8000`.

## 11. Развертывание

### 11.1 Локальный Docker-запуск

`docker-compose.yml` поднимает:

- `postgres`: PostgreSQL 16 с volume `postgres_data`;
- `backend`: Go API на `8000`, volume вложений `backend_uploads`;
- `frontend`: Vite dev server на `5173`, прокси `/api` на backend.

Команда запуска:

```bash
docker compose up --build
```

### 11.2 Production-запуск

`docker-compose.prod.yml` поднимает:

- PostgreSQL 16 без публикации порта наружу;
- Go backend без публикации порта наружу;
- nginx/frontend контейнер с публикацией `${APP_BIND:-127.0.0.1:8080}:80`.

Команда запуска:

```bash
cp .env.ps.kz.example .env
docker compose -f docker-compose.prod.yml up -d --build
```

Рекомендуемая внешняя схема:

1. Внешний nginx на VPS принимает HTTP/HTTPS.
2. Certbot выпускает TLS-сертификат.
3. nginx проксирует трафик на frontend-контейнер.
4. Frontend-контейнер отдает SPA и проксирует `/api` к backend.

### 11.3 Обновление

1. Получить новую версию кода.
2. Запустить `docker compose -f docker-compose.prod.yml up -d --build`.
3. Проверить состояние контейнеров и логи backend.
4. Перед обновлением production выполнять резервную копию PostgreSQL и upload-volume.

## 12. Безопасность

- Все закрытые операции требуют Bearer JWT.
- Пароли не должны логироваться и возвращаться API.
- Production должен использовать уникальный `KPI_SECRET`, не совпадающий с тестовым значением.
- Production должен использовать сильные начальные пароли.
- Вложения должны сохраняться под случайным внутренним именем.
- При скачивании вложения backend должен проверять право доступа к записи.
- Backend должен блокировать path traversal для внутренних имен вложений.
- На production рекомендуется ограничить CORS конкретным доменом, если backend будет доступен напрямую.
- Все данные должны передаваться пользователю по HTTPS через внешний reverse proxy.
- Роли и scope участка должны проверяться на backend, независимо от frontend-навигации.

## 13. Нефункциональные требования

### 13.1 Производительность

- Списочные API должны поддерживать пагинацию там, где объем данных может расти.
- Список KPI-записей должен ограничивать `limit` максимум 100.
- Частые выборки должны использовать индексы по месяцу, статусу, сотруднику, участку и непрочитанным сообщениям.
- Дашборд должен строиться по выбранному фильтру без загрузки лишних данных на frontend.

### 13.2 Надежность

- Backend должен создавать и дополнять схему БД при запуске.
- CSV-импорт должен быть идемпотентным.
- Изменение статуса записи и пересчет KPI должны выполняться транзакционно.
- Удаление записей и пользователей должно очищать связанные сообщения и вложения.
- Ошибки API должны возвращаться в формате `{ "detail": "..." }`.

### 13.3 Сопровождаемость

- Доменные правила должны оставаться в `internal/domain`.
- SQL-доступ должен оставаться в `internal/infrastructure`.
- HTTP-обработчики не должны дублировать расчет KPI.
- Новые бизнес-правила должны покрываться unit-тестами в доменном или application-слое.
- Документация deployment должна поддерживаться в `docs/deploy-ps-kz.md`.

### 13.4 Совместимость

- Frontend должен работать в актуальных версиях Chromium, Firefox, Safari и Edge.
- API должен сохранять JSON-контракты, используемые текущим frontend.
- SQLite-подключение может использоваться только для локальных тестов и не является production-хранилищем.

## 15. Критерии приемки

Система считается готовой к приемке, если выполняются условия:

- Пользователь каждой роли может войти и попасть на корректный стартовый экран.
- Сотрудник может создать KPI-запись без файла и с допустимым файлом.
- Сотрудник не может создать запись за другого сотрудника.
- Сотрудник не может создать отрицательный KPI.
- Начальник может подтвердить и отклонить запись своего участка.
- Начальник не может управлять сотрудниками другого участка, если у него задан участок.
- Подтверждение записи пересчитывает итоговые баллы месяца.
- Массовые KPI применяют коэффициенты `0.85` и `0.70` при превышении порогов.
- Критический KPI обнуляет месячный результат сотрудника.
- Месячные лимиты ограничивают зачтенное количество.
- Администратор может создать, изменить и удалить сотрудника.
- Администратор может создать, изменить и деактивировать KPI.
- Цели можно назначить сотруднику и группе.
- Сотрудник видит прогресс по своим целям.
- Дашборд показывает агрегаты, тренды, рейтинг, влияние лимитов и критических KPI.
- Уведомления создаются при новой записи и смене статуса.
- Мессенджер разрешает диалог начальник-сотрудник и запрещает недопустимые пары.
- Русский/казахский язык и светлая/темная тема сохраняются после перезагрузки страницы.
- Production compose запускается с обязательными секретами из `.env`.

## 16. Известные ограничения текущей реализации

- Основной production backend находится в `backend-golang/`; каталог `backend/` содержит legacy Python/FastAPI-реализацию.
- JWT хранится на frontend в `localStorage`, поэтому для production особенно важны HTTPS, защита от XSS и аккуратная работа с пользовательским контентом.
- CORS middleware backend сейчас разрешает `*`; при прямой публикации backend наружу рекомендуется ограничить origin.
- Нет отдельного refresh-token механизма; пользовательская сессия ограничена TTL access token.
- Вложения хранятся локально в Docker volume; для горизонтального масштабирования потребуется общее файловое хранилище или объектное хранилище.
- Audit log действий пользователей отдельно не реализован; история частично видна через KPI-записи, статусы, уведомления и сообщения.
